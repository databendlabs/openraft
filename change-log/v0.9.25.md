-   Fixed: [7d8bf714](https://github.com/datafuselabs/openraft/commit/7d8bf71402949d25fdaf51d801446e53581c6673) keep VecProgress sorted above granted; by Zhang Yanpo; 2026-07-28

    # Summary

    Restore the VecProgress ordering invariant whenever a voter advances
    above `granted`, so the quorum scan can no longer report a value that no
    quorum actually reached.

    # Details

    `VecProgress` keeps every entry greater than `granted` in descending
    order, and the quorum scan depends on it: for each candidate value it
    tests whether `vector[0..=i]` constitutes a quorum, which is only sound
    when that prefix really is the set of voters at or above the candidate.

    `move_up()` ran only when the updated voter had previously been at or
    below `granted`. A voter that was already above it and advanced further
    kept its old slot, leaving the greater-than-`granted` region unsorted.
    The scan then counted an arbitrary prefix as the voters that reached a
    value, and could grant a value held by fewer than a quorum, committing
    on a quorum that never existed.

    `move_up()` now runs for every voter update whose new value is above
    `granted`. Quorum recalculation still happens only when the update
    crosses the previous boundary, so already-above voters are reordered
    without adding `is_quorum()` calls.

    Backported from release-0.10 f076cf6f, where the field is named
    `quorum_accepted`. The regression test replays the five-voter sequence
    from the issue: before this fix it granted 6 although only two of five
    voters had reached it.

-   Fixed: [211b91ba](https://github.com/datafuselabs/openraft/commit/211b91baf7dd371f9522e87cffc12ab619000a75) bound the wait for RaftCore to stop on a dropped responder; by Zhang Yanpo; 2026-07-28

    # Summary

    A response channel that closes without a reply no longer joins RaftCore
    unconditionally. Callers such as `client_write`, `get_snapshot` and
    `begin_receiving_snapshot` used to block forever when the channel was
    closed by a dropped responder rather than by a core shutdown.

    # Details

    `get_core_stopped_error` awaits the RaftCore task handle to retrieve the
    error that stopped it. That is correct only when the core really has
    stopped. The state machine worker owns the responders for the commands
    it serves, so when that task dies on its own the responders drop while
    RaftCore keeps running: RaftCore only logs the failed send and continues
    its loop. Awaiting a handle that never resolves then hangs the caller
    with no timeout and no way to recover.

    Both response-receiving paths, `recv_msg` and `call_core`, now resolve
    the failure through `get_core_stopped_error_bounded`. It waits up to one
    second for the core to stop before falling back to `Fatal::Stopped`, so
    a genuine shutdown still reports the error that caused it while a
    dropped responder returns promptly.

    The wait observes the metrics watch channel instead of joining the task.
    That signal is non-destructive and safe to poll from any number of
    callers: RaftCore reports a stop in `running_state`, and the metrics
    sender is dropped when the task ends, including on a panic. Joining
    would instead consume the handle and leave `CoreState` mid-transition
    for the next caller.

    The regression test arms the memstore to panic in
    `begin_receiving_snapshot`, which kills the worker while RaftCore stays
    up. Before this change the test hangs indefinitely; now the call and a
    following `get_snapshot()` both return `Fatal::Stopped`. The injection
    point matters: panicking during `apply` instead would leave the client
    responder held rather than dropped, which is a separate failure mode
    this commit does not address.

    Backported from release-0.10, where the same repair is split across
    1d5cc706 and dd29c2e9. On 0.9 both reduce to one change, because
    `get_snapshot` and `begin_receiving_snapshot` already route through
    `call_core`. The two other APIs covered upstream, `with_state_machine`
    and `external_state_machine_request`, do not exist here.

-   Fixed: [546ed868](https://github.com/datafuselabs/openraft/commit/546ed8683b3d569fc0855bb5950d479682626b2d) handle empty limited_get_log_entries instead of panicking; by Zhang Yanpo; 2026-07-28

    # Summary

    A store that returns an empty result from `limited_get_log_entries()` for
    a non-empty range no longer panics the replication task. The empty read
    is treated as a heartbeat, so replication degrades instead of dying.

    # Details

    `limited_get_log_entries()` is documented to never return empty for a
    non-empty range, and replication relied on that by unwrapping
    `logs.first()`. The only guard was a `debug_assert!`, which is compiled
    out in release builds, so a store violating the contract panicked the
    replication task in exactly the builds that matter.

    The empty result is now handled as a heartbeat: no entries, and a
    `prev_log_id` unchanged from the request. Because `log_id_range` does not
    advance when nothing is read, retrying immediately would spin, so the
    path sleeps 10ms first and logs a warning naming the offending range.

    The impact on 0.9 is a spurious panic and a replication stall rather than
    an outage: RaftCore rebuilds the stream after the task dies, so the
    cluster recovers on its own. That recovery is also why the regression
    test cannot assert this at cluster level, and instead counts panics
    raised inside `replication/mod.rs` through a chained panic hook. Without
    the fix the test records two panics, one per follower.

    Backported from release-0.10 f994c862, where the repair lives in
    `stream_state.rs`. That file does not exist here, but the unguarded
    unwrap does, so this is a hand-port rather than a cherry-pick.

    - Fix: #1601

-   Fixed: [89629e33](https://github.com/datafuselabs/openraft/commit/89629e332ab0dcc8b7af6fa30054d7e8d0e51a51) remove the is_voter check from current_leader(); by Zhang Yanpo; 2026-07-28

    # Summary

    `current_leader()` now reports the leader from the committed vote alone.
    It previously returned `None` when the leader was not a voter, which
    contradicted `calc_server_state()` and made metrics disagree with
    themselves.

    # Details

    Openraft does not require a leader to be a voter: leadership follows from
    a committed vote, i.e. one granted by a quorum. `raft_state/mod.rs` says
    so directly and `calc_server_state()` duly reports `ServerState::Leader`
    for a non-voter leader. `current_leader()` disagreed by filtering the
    result through `membership_state.effective().is_voter()`, so the same
    node reported itself as `Leader` while `current_leader` was `None`.

    This is reachable whenever a membership change removes the leader from
    the voter set. The node keeps operating and committing until it steps
    down or a new leader is elected, and its metrics should say so.

    Dropping the check also removes the `is_voter()` scan from a hot metrics
    path, along with the TODO that asked for it to be cached.

    `check_learner_after_leader_transferred` asked `router.leader()` for the
    new leader, which scans every node. The removed node 0 still holds a
    stale committed vote for itself and now correctly reports itself as
    leader, so the test could pick it. It now asks a node that is actually in
    the new cluster.

    Backported from release-0.10 c00aa262.

    - Fix: #1693

-   Fixed: [d94e232e](https://github.com/datafuselabs/openraft/commit/d94e232e8b12265d0eb217eed779a1c8c034bdf6) ignore an election trigger on the current Leader; by Zhang Yanpo; 2026-07-28

    # Summary

    `Raft::trigger().elect()` on a node that is already the Leader is now a
    no-op. It previously started a campaign the Leader could not win, costing
    the group its Leader and inflating the term for nothing.

    # Details

    Campaigning does not tear down the internal Leader. `state.vote` moves to
    the new, uncommitted term, but the node is still leading under the old
    one, so `leader` survives with its committed vote at the previous term.
    The node keeps heartbeating from that stale leadership, which keeps
    refreshing the voters' leader leases, and an unexpired lease is exactly
    what makes them reject the vote request the campaign just sent. The
    campaign cannot succeed, and repeating the trigger only repeats the loop.
    The old code acknowledged the gap with a `TODO: reject if it is already a
    leader?`.

    `Engine::elect()` additionally asserts that leadership has been
    relinquished. Campaigning while `leader` is set leaves
    `leader.vote` a term behind `state.vote`, which is the inconsistency
    `LeaderHandler` would then operate on, so it is worth catching in debug
    builds rather than letting it propagate.

    `test_elect_single_node_elect_again` built exactly that forbidden state,
    a committed leader vote plus a second `elect()`, to check that a later
    campaign overrides an earlier one. It now runs two real campaigns instead
    and is renamed to say what it covers.

    Backported from release-0.10 4490c678, minus the Pre-Vote half: 0.9 has
    no Pre-Vote, so `elect()` takes no `pre_vote` argument and the trigger
    has no non-disruptive variant to fall back on.

-   Fixed: [81e304b5](https://github.com/datafuselabs/openraft/commit/81e304b589ee6935696fea2d33c0073c829f0412) send a snapshot to a follower behind a fully purged log; by Zhang Yanpo; 2026-07-28

    # Summary

    When the leader has purged its entire log and a follower's progress is
    reset, `next_send()` now returns a snapshot. It previously returned
    `Inflight::None` on every call, so the follower never probed, never
    received a snapshot, and could not converge until a new entry was
    proposed.

    # Details

    `next_send()` already sends a snapshot when every candidate matching
    position is purged, that is `searching_end < purge_upto_next`. That test
    misses the boundary case where the two are equal, which is what
    `purge_upto == last_log_id` with a reset progress produces: the check is
    skipped, `start` is clamped up to the purge boundary and lands on
    `last_next`, `end` clamps down to the same value, and the empty range
    falls into the `Inflight::None` arm. Nothing advances the state, so the
    next call computes the same thing.

    The empty range now sends a snapshot, but only while still probing, i.e.
    `matching.next_index() < searching_end`. That distinction matters: a
    follower that is fully caught up reaches `start == end` on every call
    too, and must keep returning `Inflight::None`. Without the guard every
    idle follower would be shipped a snapshot.

    Backported from release-0.10 afd6508b. Upstream restructures `next_send`
    into explicit probing and pipeline regimes, where this case falls out of
    the probing branch. 0.9 has no pipeline mode, so the port keeps the
    existing shape and adds the probing condition directly.

    - Fix: #1828

-   Fixed: [c9520f1d](https://github.com/datafuselabs/openraft/commit/c9520f1dea3f5a7d2e169c4081748f9008938f9a) don't abort publish script for already-published crates; by Zhang Yanpo; 2026-07-28

    # Summary

    crates.io rejects API requests without a descriptive User-Agent (403),
    so every existence check in the publish script silently read as "not
    published." Re-running the script after a partial publish therefore
    always retried `cargo publish` and aborted the whole run instead of
    skipping the crate that was already there.

    # Details

    - Send a descriptive User-Agent on the crates.io API check, fixing the
      false negatives that made already-published crates look unpublished.
    - If `cargo publish` still fails, inspect its output for "already
      exists on crates.io index" and treat that as success rather than
      aborting, covering the race between our own check and the publish
      attempt.
    - Replace the flat 30s post-publish sleep with a poll loop that checks
      crates.io every few seconds (up to a bounded timeout), so the script
      moves on as soon as the new version is actually indexed.
    - Log the resolved HTTP status on every existence check so a future
      failure is self-diagnosing instead of requiring another investigation.

    Backport of ee915f5c from release-0.10.

-   Fixed: [2447bae4](https://github.com/datafuselabs/openraft/commit/2447bae4f941ec2574afff907aa70be2b7788498) avoid blocking RaftCore on closed replication; by Zhang Yanpo; 2026-07-28

    # Summary

    Removed replication tasks are now joined in the background, so a follower
    that stops responding no longer freezes the leader while replication
    streams are rebuilt.

    # Details

    `remove_all_replication()` awaited every removed task inline, inside the
    RaftCore loop. A task sitting in an AppendEntries call to an unresponsive
    follower only returns after the RPC times out, so each rebuild stalled
    RaftCore for up to one RPC timeout per removed target. Rebuilds happen on
    every membership change and on every leadership establishment, and while
    RaftCore is parked it serves neither writes, nor reads, nor metrics.

    Detaching the join lets a removed task outlive its replacement, so it can
    still deliver progress. That progress is discarded by the existing
    `session_id` check in `does_replication_session_match()`: every caller of
    `rebuild_replication_streams()` has changed either the leader vote or the
    effective membership log id, so a detached task's session id never
    matches again. This is the same guard 0.10 added explicitly as a stream
    id.

    The regression test blocks AppendEntries to a learner, leaves the
    replication task inside that call, and requires the following
    `add_learner` to finish well within the RPC timeout. The router gained
    `set_rpc_blocked()` for it: unlike `set_unreachable()`, the RPC future
    never resolves, which is what puts the task where the defect needs it.

    Backport of 369e5d1c from release-0.10.

    - Fix: #1810

-   Fixed: [7b66adf2](https://github.com/datafuselabs/openraft/commit/7b66adf26cde8c0332918ca036ff805cff55f2df) reset purged membership on snapshot install; by Zhang Yanpo; 2026-07-28

    # Summary

    Installing a snapshot now replaces a local effective membership whose
    backing log entry the snapshot purges, instead of leaving the node running
    a membership config that no longer exists anywhere.

    # Details

    `MembershipState::update_committed()` decided whether to replace the
    effective membership by comparing log indexes alone. A follower that had
    accepted a membership entry from an old leader, then received a snapshot
    whose last membership sits at a lower index, kept that local effective
    membership -- while the same snapshot install set `purge_upto` to the
    snapshot's last log id and deleted the entry backing it. The node was then
    left with a membership config that neither the log nor the snapshot could
    restore, permanently diverged from the cluster.

    The method now takes the snapshot's last log index and, when the effective
    membership falls within the purged range, resets both committed and
    effective to the snapshot's membership. The index comparison is kept for
    the uncovered case, where the local effective membership is still backed
    by a log entry. The boundary is inclusive: purging goes up to and
    including the snapshot's last log index.

    This path is only reachable from `install_full_snapshot()`, which is why
    the snapshot index can be threaded through `update_committed()` rather
    than through a separate entry point as on 0.10.

    Backport of 01e813a5 from release-0.10.

    - Fix: #1808
